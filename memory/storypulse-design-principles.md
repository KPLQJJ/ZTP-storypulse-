# StoryPulse 界面设计原则

从用户体验出发，只保留可迁移到任何网文审稿平台的通用原则。不绑定具体作品、章节、作者。使用"应/不应/建议/避免"指令性语言。

## 信息架构

- **导航应反映核心工作流顺序**：管理作品 → 提交审稿 → 查看结果 → 积分消费。侧边栏菜单应按此逻辑分组，而非按功能模块平铺。
- **每个页面应有单一明确职责**。列表页不应嵌入创建表单，详情页不应承载批量操作。
- **页面标题应始终可见**。Header 面包屑应清晰显示当前位置，避免用户迷失。

## 视觉层次

- **品牌色应克制使用**。陶土/赭石色（brand-600: #a8592b）应仅用于主行动按钮、选中态、关键数据高亮三类场景。不应出现在装饰性元素、普通文本、或非交互区域。
- **字体层级不应超过 4 级**。页面标题（h1, 2xl bold）→ 区块标题（h2, base semibold）→ 正文（sm）→ 辅助文本（xs muted）。避免引入第 5 级字号。
- **卡片应作为信息容器的主要形式**。列表项、详情区块、统计概览均使用 Card 组件，通过统一的内边距和圆角建立视觉节奏。
- **间距应保持 8px 基准**。自定义间距不应使用 8 的倍数以外的值。

## 交互反馈

- **每个操作应有三种状态**：进行中（loading）、成功（toast 或跳转）、失败（toast + 原因）。不应出现点击后无反应的情况。
- **破坏性操作应有二次确认**。删除作品、删除章节、退出登录必须通过 Dialog 拦截，不应直接执行或使用浏览器原生 confirm()。
- **触屏设备上操作入口应始终可见**。不应依赖 hover 显示菜单或操作按钮——使用 `@media (hover: none)` 为触屏提供 fallback。
- **表单提交后应清空或跳转**。新建/编辑表单成功后应有明确的状态变更，避免用户重复提交。

## 内容策略

- **空状态应有引导性文案和行动召唤**。如"还没有作品"应配合"创建第一部作品"按钮；不应只显示空白区域或纯文字提示。
- **错误提示应说明原因和建议方案**。如"网络请求失败，请检查连接后重试"，不应只显示"加载失败"。
- **术语应全局一致**。全文统一使用"作品"而非混用"小说/书籍"；统一使用"审稿"而非混用"评审/审核"。
- **数值应格式化显示**。积分用千分位分隔，字数超过万时用"万"为单位，百分比保留一位小数。

## 性能感知

- **加载态应使用 Skeleton 而非空白旋转器**。Skeleton 应模拟目标内容的形状，让用户预知即将出现的内容布局。
- **页面级切换应有 Suspense 边界**。路由懒加载时，fallback 应是一个完整的页面骨架而非单一 spinner。
- **后台数据刷新不应阻塞交互**。加载新数据时不显示全页 loading。

## 适用范围

后续 UI 开发中，所有新增或修改的界面应参照以上原则。如某一原则在某场景下不适用，应在实现时明确记录例外理由。
